1.0 Introduction  
 
 
1.1 Purpose  
This document outlines the requirements for developing an online food ordering and delivery platform, 
which allows users to browse the menus of partner establishments and place orders based on their 
preferences.  
 
1.2 Overview of Document  
The document includes the general description of the system, the functional and non -functional 
requirements, the data description, and the user documentation. Each section provides detailed 
specifications for the implementation of the platform.  
 
1.3 Operating  Enviro nment  
 
 


   
 
   
 The P.A.D.A. (Pastry And Delicious Aliments) system has three active roles (actors) that connect to 
the platform as regular users. The Customer, the Order Manager, and the Admin. The interaction of 
all three roles with the central service (P.A.D.A. Service ) requires authentication (Log in / Log out) in 
order to gain access to the corresponding management or shopping environment.

3.1.8.0 Update Store Page  
Use Case Name  Update store page  
Actor  Store Manager  
Trigger  The Store Manager decides to update the data, status or items 
of the store page.  
Precondition  1. The Store Manager has successfully logged in to the system.  
2. The store already exists in the system.  
Basic Path  1. Store Manager selects the "Update store page" action.  
2. The system displays the current store page information.  
3. The Store Manager chooses what he wants to update: items, 
store status, item price.  
4. The Store Manager makes the changes.  
5. The system checks the validity of the data after the change.  
7. The system saves the changes and updates the database  
8. A successful update message is displayed.  
Alternative Paths  - 
Postcondition  1. Changes to the store page, products, prices or status are 
permanently stored in the system.  
2. The store page is updated immediately and is visible to 
customers with the new information.  
Exceptions Paths  1. Data Validation Failure: If some item elements are incorrect or 
empty the system displays an error message and the changes 
are not saved.  
2. If the Store Manager does not have permissions, i.e. 
unsuccessful login, a relevant message appears, e.g. "Access 
Denied".  

   
 
   
  
3.1.8.1 Items  
 Use Case Name  Items (Product Management)  
Actor  Store Manager  
Trigger  The Store Manager selects the product section.  
Precondition  1. Store Manager is connected to the system.  
2. Store Manager is located in the store management 
environment.  
Basic Path  1. The Store Manager selects the Items menu.  
2. The system retrieves from the database and displays the list 
of all registered products in the store.  
3. For each product, basic information (Name, price, availability) 
is displayed.  
4. Store Manager checks the information.  
5. The system displays the available options.  
6. The Store Manager chooses whether to make a change.  
7. The system updates the items list.  
8. A relevant message appears.  
Alternative Paths  - 
Postcondition  The store's product catalog is updated in the database (new 
additions, availability changes, or deletions).  
Exceptions Paths  1. If some fields are empty or invalid, the system displays an error 
message and the item is not saved during create.  
2. If saving a change to the database fails then the system 
displays a message and the changes are not completed.

3.1.10.0 Validate Order  
Use Case Name  Validate Order  
Actor  Store Manager  
Trigger  The customer submitted an order with the instructions field filled 
out, and the system flagged it.  
Precondition  - 
Basic Path  1. The system sends the flagged order to the Store 
Manager.  
2. The order appears as an option in the Store Manager 
Panel.  
3. The Store Manager clicks on the order box.  
4. The system displays the order details.  
5. The Store Manager reviews whether it is valid or not.  
6. The Store Manager rejects it.  
7. The Store Manager reports it.  
8. The Store Manager accepts it.  
Alternative Paths  1. The system sends the flagged order to the Store Manager.  

   
 
   
 2. The order appears as an option in the Store Manager Panel.  
3. The Store Manager has the automated review feature

3.2 Non -Functional Requirements  
 
3.2.1 Performance Requirements  

   
 
   
 The performance should be as fast and as responsive to the user’s needs as possible. This means 
that delays should be non -existent, excluding 2 very specific scenarios: Sending an order with the 
instructions field filled and updating an order after it was submitted.  
3.2.2 Safety Requirements  
Regarding user data safety, ALL data will be backed up into a different database completely 
disconnected from the main one. Both of the databases will contain encrypted user data to protect 
user’s privacy.  
Regarding store safety, ALL stores will have at least 1 store manager to help moderate orders with 
instruction and all store manager will be able to directly communicate with admins.  
 
3.2.3 Security 
As stated above in the Safety Requirements, ALL user data will be encrypted and stored in 2 
databases (1 normal and 1 back up).  
Account data will be protected by a simple email and password log in with the ability to have 2FA if 
the user wants it.  
 
3.2.4 Software Quality Attributes  
The website should be online almost 99% of the time, with that 1% being for maintenace.  
The website will be as lightweight as the user desires, having features that are resource intensive, like 
animations, be turned off, either automatically when the site detects a user with a lower end device, or 
manually by the user themselves.  
 
3.2.5 Business Rules  
NEVER sell user data.  
User satisfaction is far more important.  
User data MUST be protected at all costs  
User privacy is TOP priority
